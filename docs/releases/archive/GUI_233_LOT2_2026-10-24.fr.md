# Babet 2.33.0 — lot 2 : fichiers déposés et tags TextView

## Application

Ce lot s'applique sur le lot 1 validé, y compris ses correctifs de documentation
et de test des sélecteurs. L'archive contient uniquement les fichiers modifiés
ou ajoutés, avec leurs chemins relatifs à la racine du projet. Extraire à cette
racine en remplaçant les fichiers, puis lancer :

```bash
set -o pipefail
./run_tests.sh --release 2>&1 | tee babet-tests-233-lot2.txt
```

Aucune suppression ni modification manuelle de source n'est nécessaire. La
version CMake reste 2.33.0, déjà préparée au lot 1. Aucun tag ni publication Git
n'est effectué par ce correctif. Les PDF seront à régénérer lors de la release.

## Ajouts

- `setDropTypes({"text"|"files", ...})`, avec groupe de symboles optionnel GTK
  4.6 pour les fichiers. Le callback `onDrop` reçoit `kind` en sixième argument.
  Les chemins locaux sont copiés dans l'ordre avant l'appel Lua ; les URI
  distantes sont filtrées et une liste sans chemin local est refusée.
- `createTag`, `applyTag`, `removeTag`, `removeAllTags`, `tagsAt`, `tagRange`,
  `offsetAt` pour TextView (GTK 4.0). Les plages sont des indices d'octets Lua
  inclusifs et doivent respecter les limites UTF-8. Les propriétés utilisent
  des GValue typés et le setter natif non variadique.
- Documentation française et anglaise, changelogs, exemple générique
  `examples/gui_rich_text/main.lua` et intégration des régressions au lanceur.

Les plages sont suivies par GTK, pas par une copie des applications côté Babet.
`setText` conserve les définitions et efface les applications. La détection de
position utilise les coordonnées locales et la dernière allocation GTK.

Le choix historique MOVE est conservé. Pour importer des fichiers externes,
configurer explicitement `setDropActions("copy")` : Babet transmet des chemins,
mais n'effectue aucune copie de fichiers. Les callbacks à arguments fixes
restent compatibles ; un callback variadique voit désormais six arguments.

## Durée de vie et erreurs

Les copies de texte/chemins natifs et les références temporaires de tags sont
libérées par RAII. Les tables et chaînes de callback sont créées dans l'appel
Lua protégé. Les exceptions C++ pendant une copie de dépôt refusent le transfert
et ne traversent pas GTK. L'état logique d'un récepteur est conservé pendant les
allocations Lua susceptibles de déclencher un finalizer ; les itérateurs natifs
ne sont pas réutilisés après une allocation Lua.

Changer les formats pendant le signal `drop` renvoie une erreur. Une modification
pendant le survol refuse le transfert courant. Les règles existantes sur les
cibles imbriquées, `onDrop(nil)` et les actions restent applicables.

## Vérifications réalisées

Validation ciblée avec les véritables `gui.cpp`, chargeur GTK, gestion du thread
principal et état processus, liés à Lua 5.5.1. Le petit exécutable de validation
remplace seulement les services curses/signaux sans rapport avec ces tests ;
il ne remplace pas les bindings GUI. Compilation C++23 avec les avertissements
`-Wall -Wextra -Wpedantic -Werror`.

Les contrats couvrent les caractères multi-octets, plages scindées/fusionnées,
propriétés natives typées, conservation des définitions, capacités GTK absentes,
refus du dépôt, URI distantes, préchargement tardif, callback en erreur,
reconfiguration, désactivation et fermeture de la fenêtre pendant le dépôt.
Le test réel vérifie aussi un TextView non éditable et insensible, les positions
sous les glyphes et l'interdiction de modifier les tags dans `onDraw`.

Le nouveau scénario de fermeture a également révélé un défaut de l'émetteur de
fichiers simulé : il retenait la fenêtre que le faux GTK détruit explicitement.
Il utilise maintenant le mécanisme de rétention des chemins de widgets déjà
employé par les tests DND, qui exclut cette fenêtre simulée.

## Limites et suite

- La compilation complète de Babet et `./run_tests.sh --release` restent à lancer
  sur le poste utilisateur après application de ce lot.
- Le dépôt de fichiers externes est testé avec un émetteur simulé. Le trajet
  complet depuis un gestionnaire de fichiers réel n'a pas été exercé ici.
- LeakSanitizer ne peut pas fonctionner dans cet environnement : un programme
  témoin qui fuit échoue sur l'accès à `/proc/.../task`. Les tests locaux ASan
  utilisent donc `detect_leaks=0`, tout en conservant les contrôles d'accès mémoire
  et UBSan. Les compteurs du faux GTK vérifient la libération des objets et copies
  après chaque état Lua. Le script livré n'abaisse pas la détection des fuites
  des tests hermétiques sur le poste utilisateur.
- Le backend GTK extrait et Xvfb sur TCP ont été employés uniquement dans le
  harnais local ; les scripts livrés utilisent le GTK système et leur Xvfb privé
  habituel. Le test réel conserve l'isolation du portail des sélecteurs du lot 1.
- Le lot 3 reste à faire : image du presse-papiers, miniatures, `openUri`,
  `launchFile`, `idle`, `timeout`, `cancel`.
