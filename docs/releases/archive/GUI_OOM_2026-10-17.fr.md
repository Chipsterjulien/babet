## Corrections

### Préparation du callback `onDrag`

L’allocation Lua de la chaîne de phase se faisait avant l’appel protégé.
Un échec pouvait donc remonter à travers la pile native GTK. La résolution du
callback, la construction des arguments et l’appel utilisateur sont désormais
dans un même appel protégé. L’état logique du widget est conservé pendant ce
passage, y compris si le ramasse-miettes ou un callback détruit le widget.

### Copies de texte et setter `TextView`

La copie de texte renvoyée par `g_object_get` est désormais détenue par un
objet C++ qui la libère même si la construction du `std::string` échoue.
Le setter conserve ses références native/logique et son thread de callback
dans une garde qui les restaure à la sortie, normale ou exceptionnelle.

Une erreur lors de la copie effectuée après la mise à jour peut laisser le
nouveau texte déjà présent dans GTK ; `setText` n’est pas transactionnel.
L’erreur reste signalée par `nil, erreur`, et les ressources et callbacks
restent utilisables. L’API publique et les notifications en cas de succès
conservent leur comportement.

## Régressions ajoutées

- Injection d’échecs d’allocation Lua pendant les événements de déplacement,
  sans `lua_pcall` extérieur au pont GTK : une erreur non contenue fait échouer
  le test. Vérification de la pile, de la récupération, de l’auto-retrait du
  callback et du nettoyage des 32 états Lua.
- Injection d’exceptions `std::bad_alloc` dans `getText`, puis dans chacune
  des deux copies de `setText`, avec des cas témoins sans erreur.
- Comptage des copies de texte et des objets du faux GTK, restauration du
  thread principal après un setter en coroutine, récupération après erreur,
  setter réentrant et fermeture/finalisation depuis le callback.

Les compteurs appartiennent uniquement au faux GTK des tests. Aucun mécanisme
d’injection d’erreur n’a été ajouté au runtime de production.
Les diagnostics `babet.gui callback error: not enough memory` émis pendant
ces tests correspondent aux fautes injectées ; les lignes `[PASS]` et le code
de sortie du test déterminent son résultat.

## Vérifications locales

Compilation ciblée du code modifié en C++23, avec avertissements traités
comme erreurs. Tests exécutés en mode normal et sous ASan/UBSan :

| Test | Résultat |
| --- | --- |
| Allocations `onDrag` | 32 cas : 2 avec erreurs injectées, 30 témoins ; récupération et nettoyage OK |
| Allocations `TextView` | 5 cas : 3 avec erreurs injectées, 2 témoins ; tampons, références et callbacks OK |
| Entry | 7/7 |
| DrawingArea, dont rendu Cairo réel | 12/12 |
| Widgets, CSS, gestes, réordonnancement | 8/8 |
| Exécution GUI et application embarquée | 10/10 |

Contrôles structurels GUI : 33/33, 35/35 et 85/85. Orchestration de release :
9/9. La régression d’allocation DrawingArea existante passe également en mode
normal (32 cas).

Contrôles négatifs : le nouveau test refuse le code de l’archive d’origine
pour `onDrag` et pour les copies de texte. Il refuse également une variante
où seule la garde du setter est retirée : le callback repart alors sur le
mauvais thread Lua.

Limites : cette validation utilise le vrai code Babet et Lua 5.5.1 avec un
faux GTK déterministe ; le test DrawingArea utilise aussi le vrai Cairo.
Les exécutables ciblés réutilisent des objets inchangés des validations
précédentes. Ce n’est pas une reconstruction complète de la release.
GTK réel/Xvfb n’est pas disponible dans cet environnement.

LeakSanitizer échoue ici parce qu’il ne peut pas inspecter `/proc/.../task`.
Les essais ASan/UBSan locaux ont donc été exécutés avec `detect_leaks=0`.
Cette option n’est pas ajoutée aux scripts livrés : la campagne `--release`
du mainteneur doit confirmer la détection des fuites sur sa machine.
