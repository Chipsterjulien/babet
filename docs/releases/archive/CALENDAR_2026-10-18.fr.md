# Babet — tests des marqueurs et de la navigation Calendar

Complément du 18 octobre 2026, à appliquer au projet contenant déjà :

```lua
calendar:markDay(day)
calendar:unmarkDay(day)
calendar:clearMarks()
calendar:onViewChanged(function_or_nil)
```

Ce lot renforce les tests. Il ne modifie ni `src/`, ni la version de CMake,
qui reste 2.29.0 pendant la validation de cette nouvelle API.
`setDate()` ne déclenche pas `onViewChanged()` : le callback concerne la
navigation native de l'utilisateur. Les applications qui changent la date
par programme doivent aussi rafraîchir leurs marqueurs explicitement.

## Contenu du ZIP

- `tests/gui/fake_gtk4_runtime.c` : navigation native simulée, avec date mise à
  jour avant le signal, ajustement du jour et observation des marqueurs.
- `tests/gui/calendar_view_contract.lua` : six scénarios, couvrant les quatre
  directions, février bissextile, décembre/janvier, marqueurs, remplacement et
  retrait du callback, erreur/yield, setter réentrant et fermeture de fenêtre.
  Les cycles de callbacks et les références natives sont également contrôlés.
- `tools/test_gui_widgets.py` : exécution des scénarios, vérification des
  marqueurs réellement conservés par le faux GTK, quatre échecs de connexion
  des signaux de navigation et compteur calculé à partir des cas réussis.
- `tests/gui/real_gtk_calendar.lua` et `tools/test_gui_real_gtk.py` : scénario
  optionnel avec GTK4, Xvfb et XTest. Un clic donne le focus au calendrier ;
  six raccourcis Ctrl+flèches provoquent les changements de mois/année. Chaque
  événement est acquitté par Lua, puis le dernier ferme la fenêtre depuis le
  callback. Le bilan de cette suite est aussi calculé automatiquement.
- `CHANGELOG.md`, `CHANGELOG.fr.md` et cette note.

Les deux outils Python sont déjà appelés par `run_tests.sh` ; aucun changement
supplémentaire de ce script n'est nécessaire pour `--release`.

## Vérifications locales

Les tests dynamiques utilisent Lua 5.5.1 et un petit hôte compilant les vrais
bindings GUI, le chargeur GTK et la gestion d'état du projet. Seuls les services
curses/signaux sans rapport avec ces scénarios sont remplacés dans cet hôte.
Ce n'est pas une compilation complète de Babet.

- Widgets avec faux GTK : **18 PASS / 0 FAIL**, en normal puis avec ASan/UBSan
  sur l'hôte et le faux GTK.
- Contrats structurels widgets : **91 PASS / 0 FAIL**.
- Contrats structurels runtime GUI : **35 PASS / 0 FAIL**.
- Chargeur GTK : **17 PASS / 0 FAIL**.
- Régressions d'allocation `onDrag` et TextView : **2 PASS** avec ASan/UBSan.
- Contrôle négatif : un hôte privé avec `calendar_view_changed` désactivé échoue
  sur « not all four native navigation signals reached Lua ». Cette mutation
  sert uniquement à vérifier le test ; aucun code muté n'est livré.
- Syntaxe Python et Lua des fichiers ajoutés/modifiés : vérifiée.

Limites : le scénario avec GTK réel n'a pas pu être exécuté ici, car Xvfb est
absent. LeakSanitizer échoue dans cet environnement lors de l'inspection de
`/proc/.../task` ; les passes ASan/UBSan locales ont donc été faites avec
`detect_leaks=0`. Cette restriction locale n'est pas ajoutée aux tests
hermétiques livrés. Le test d'intégration GTK conserve son réglage préexistant
pour les caches des bibliothèques système. Aucun résultat de validation complète
`--release` n'est annoncé dans ce bilan.

## Application et validation complète

Extraire le ZIP à la racine du projet, en remplaçant les fichiers existants :

```bash
unzip -o /chemin/vers/Babet_Calendar_tests_fichiers_modifies_20261018.zip -d .
./run_tests.sh --release
```

Le script produit le journal `babet-tests.txt`, à transmettre pour la suite.
La suite widgets doit afficher **18 PASS**. La suite avec GTK réel doit afficher
**4 PASS** lorsque GTK4, Xvfb et XTest sont disponibles ; sinon elle indique
explicitement **SKIP**. Il n'est pas nécessaire de reconstruire les manuels PDF
pour appliquer ce complément de tests.


## Clôture après validation du 18 octobre 2026

Le journal `babet-tests(20261018-152314).txt` fourni par Julien confirme la
validation complète `--release` : ASan/UBSan OK, build normal final OK et
11 tests réseau réussis sans avertissement. Les widgets passent 18/18 et
l'intégration GTK réel 4/4, dans les deux builds ; la navigation Calendar n'est
pas ignorée. Les cas UPX et sudo/PTY indiquent leurs indisponibilités respectives.
Ces résultats complètent les limites de préparation décrites plus haut.

Les deux manuels GUI précisent désormais que `setDate()` n'émet pas
`onViewChanged`, que les marqueurs persistent par numéro de jour et que la
navigation peut ajuster le jour sans `onChanged`. Ils décrivent aussi la date
intermédiaire observable lors de la sélection d'un jour grisé. L'exemple
reconstruit les marqueurs à l'initialisation, après navigation native et après
un changement de date programmatique. Les chemins correspondants ont été relus
dans [GTK 4.14.5](https://github.com/GNOME/gtk/blob/4.14.5/gtk/gtkcalendar.c) :
`calendar_set_month_next`, `calendar_select_day_internal`,
`gtk_calendar_button_press` et `gtk_calendar_select_day`.

Le contrôle de propreté de `test_gui_widget_contracts.sh` refuse maintenant
les motifs `README_PATCH_*` et `LIRE_*` à la racine, y compris les liens cassés.
Les notes conservées dans `docs/releases/archive/` restent autorisées.

Ce complément de documentation ne modifie pas le runtime et ne crée aucun tag.
La version source reste 2.29.0 ; une future publication 2.30.0 sera cohérente
avec l'ajout de ces API publiques, après mise à jour des fichiers de version.

### Application du complément de documentation

Extraire `Babet_Calendar_documentation_fichiers_modifies_20261018.zip` à la
racine du projet. Un ZIP de fichiers modifiés ne supprime pas les anciens
fichiers : supprimer ensuite uniquement `README_PATCH_CALENDAR.md` à la racine,
dont le contenu est conservé et complété dans la présente archive.

```bash
rm -f -- README_PATCH_CALENDAR.md
bash tools/test_gui_widget_contracts.sh
```

Le contrôle doit afficher **91 PASS / 0 FAIL**. Les deux manuels PDF reconstruits
sont inclus dans le ZIP, avec les sources Markdown correspondantes. Une nouvelle
compilation complète n'est pas nécessaire pour ce complément documentaire.
