# Lot verrou — 25 octobre 2026

Base : archive complète `v21 (Copie)(20261025-074823).zip` reçue pour Babet.
Ce lot prépare la primitive de verrou prévue pour 2.34 ; il ne constitue pas
une release. La version source du ZIP de départ (2.33.0) est conservée pendant
ce développement. Il faudra aligner CMake, changelogs et manuels lors de la
préparation de la release finale.

## Livraison

- `babet.lockFile(path)` → poignée, nil ; nil, `"locked"` pour contention ;
  nil, diagnostic pour une autre erreur. Aucun contenu écrit automatiquement.
- `lock:write(text)` → true, nil ou nil, diagnostic. Écriture sur le même
  inode, sans remplacement du fichier ; une erreur garde le verrou.
- `lock:close()`, `<close>`, GC et fermeture d'état Lua. Le fichier demeure
  permanent, y compris après fermeture et arrêt brutal du processus.
- `flock` et `O_CLOEXEC`. Registre de poignées partagé par les états Lua et
  nettoyage après `fork()` par `close()` dans l'enfant, sans `LOCK_UN`.
- Vérification du type avant ouverture I/O : inode épinglé par `O_PATH`, puis
  réouvert via `/proc/self/fd`. Cette protection exige procfs pour les fichiers
  existants, également en embedding.
- API enregistrée dans le runtime commun, test de surface exacte mis à jour,
  documentation FR/EN et ajout des chapitres à l'ordre des futurs manuels PDF.

## Vérifications effectuées

Sur le binding compilé avec Lua 5.5.1 du projet :

| Vérification | Résultat |
| --- | --- |
| Harnais natif, compilation `-Wall -Wextra -Wpedantic -Werror` | 4 groupes PASS |
| Même harnais avec UBSan | 4 groupes PASS |
| Même harnais avec ASan + UBSan, `detect_leaks=0` | 4 groupes PASS |
| Tests Python/Lua, runner isolé normal | 8 groupes PASS |
| Tests Python/Lua, runner isolé ASan + UBSan, `detect_leaks=0` | 8 groupes PASS |
| Syntaxe C++ de `runtime_registration.cpp` avec la nouvelle déclaration | OK |
| Syntaxe Bash des scripts modifiés et compilation Python | OK |

Le harnais natif vérifie les descripteurs `FD_CLOEXEC`, un enfant forké qui
reste vivant sans retenir le verrou ni déverrouiller son parent, 60 cycles
d'états Lua avec 9 pannes d'allocation effectivement déclenchées, récupération
après ces pannes, concurrence entre deux threads Lua et 30 forks. Les erreurs
d'I/O injectées couvrent EINTR, écritures courtes/nulles, ENOSPC et échec de
troncature ; la contention native reste effective après chaque erreur.

Les tests Python confrontent Babet au `flock` de Python et à d'autres processus :
unicité du gagnant dans huit courses, liens symboliques/physiques, inode et
contenu préservés, fermeture d'un descripteur indépendant, `kill -9`, fils
exécuté encore vivant après la fin du lanceur, FIFO/périphérique/dossier
refusés, contrat Lua, fermeture explicite, GC et `<close>`.

## Limites de cette validation

- Pas de compilation complète ni de `./run_tests.sh --release` ici. La suite
  complète doit encore confirmer l'intégration dans le runtime et les workers.
  Le cas worker est livré et appelé par le harnais Python avec un vrai Babet ;
  `--standalone` le saute explicitement sur le runner isolé.
- LeakSanitizer échoue ici avec `Can't open /proc/.../task for reading`, même
  sur un exécutable dont `main()` ne fait rien. ASan/UBSan ont donc tourné avec
  la détection LSan désactivée ; les tests de comptage des descripteurs passent.
  Le script livré ne désactive pas LSan : ton environnement garde ses réglages.
  Le binding et le harnais sont instrumentés, l'archive Lua réutilisée ne l'est pas.
- Pas de validation sur NFS/SMB ni sur architecture 32 bits. Le contrat cible
  les systèmes de fichiers Linux locaux et des applications coopérantes.
- Les manuels PDF sont à régénérer pour la release ; seuls les chapitres sources
  et leur ordre sont mis à jour dans ce lot.
- Ce lot ne modifie pas les fonctionnalités GTK. Le cas de négociation DND
  COPY/MOVE entre cibles imbriquées signalé dans la revue précédente reste
  distinct et n'est pas corrigé par ce ZIP.

