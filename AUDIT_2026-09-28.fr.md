### Test hors de `$TMPDIR` et remplacement atomique

La petite application de vérification est créée et exécutée dans un dossier
privé `build/deploy-smoke.*`, nettoyé à la sortie. Un `$TMPDIR` monté `noexec`
ne bloque donc plus cette étape ; l'arborescence de build doit, comme pour

un temporaire dans le même dossier que `/usr/local/bin/babet`, le remplit avec
`install -m 0755`, puis le publie par `mv -fT`. Un processus déjà lancé garde
son ancien inode ; une erreur pendant la préparation conserve l'ancien chemin
et son contenu. `-T` empêche de déplacer le temporaire dans un répertoire
accidentellement présent à la place du binaire. Un lien symbolique au chemin
final est remplacé, sans modifier sa cible.

Un seul shell, lancé via sudo si nécessaire, effectue cette installation et
possède son propre nettoyage. Les erreurs et les signaux HUP/INT/TERM retirent
le temporaire. SIGKILL ou une coupure peuvent laisser un temporaire ; le
remplacement garantit une visibilité atomique, pas une durabilité après panne
électrique fondée sur `fsync`. Aucun contrat du runtime C++ n'est modifié.

## Quatrième revue : déploiement UPX, lot 16

La régression signalée par Claude est confirmée sur le runtime du lot 15 avec
le binaire Linux amd64 officiel d'[UPX 5.0.2](https://github.com/upx/upx/releases/tag/v5.0.2).
Après compression `--best`, `--version` réussit mais `-c` renvoie le code 1 et
`missing executable image descriptor`. L'identité chargée reste correcte ; le
descripteur à patcher n'est plus visible dans les octets du fichier compressé.
Le script `build_and_deploy.sh` effectuait cette compression dès qu'UPX était
présent, alors que `release.sh` ne l'effectuait pas.

**Choix retenu :** conserver le format d'image du lot 15 et retirer UPX du
déploiement automatique. Ajouter uniquement un test après installation aurait
détecté le problème après avoir remplacé le Babet fonctionnel, sans réparer la
compatibilité. Le script vérifie désormais, avant toute installation, que le
runtime peut créer puis lancer une petite application. Un échec interrompt
le déploiement ; son répertoire temporaire est nettoyé. Le diagnostic natif
mentionne un runtime potentiellement compressé ou réécrit (UPX) et conseille
de reconstruire puis d'utiliser le runtime sans compression. Aucune
décompression automatique ni dépendance UPX du builder n'est introduite.

Le nouveau préflight exécute huit scénarios du vrai script avec compilation
simulée et installation redirigée vers un dossier privé : branches root/sudo,
UPX présent/absent, échec de compilation, binaire manquant, échec du builder,
échec de l'application générée et résultat incorrect. Il vérifie la conservation
de l'installation précédente sur échec, l'ordre des contrôles, le nettoyage
et l'absence d'appel à UPX. Deux vérifications locales supplémentaires emploient
le runtime réellement compilé, avec les opérations privilégiées toujours
redirigées. Aucune installation dans `/usr/local/bin` n'est effectuée par ces
tests. Le nouveau préflight échoue bien sur l'ancien script.

`test_image_identity.py` conserve les 22 scénarios du lot 15 et ajoute un cas
réel UPX optionnel : version lisible, builder refusé avec le nouveau diagnostic,
sortie précédente préservée et aucun temporaire de publication restant. Ce cas
est réservé au build normal ; absence d'UPX ou refus du format par l'outil

Les règles `__pycache__/` et `*.py[cod]` sont ajoutées au `.gitignore`. Le ZIP

## Troisième revue : correctifs du lot 15

La base est le lot 14 complété par 14b et son bilan de validation final.
Les trois observations de Claude sont confirmées sur cette base :

- une copie du runtime nu suivie d'une fausse signature `PK\5\6` et de
  bourrage refusait de démarrer avec une erreur miniz. C'est une régression du
  lot 14. Le sondage de 3 241 ELF et ses huit résultats rapportés par Claude
  n'ont pas été refaits ; notre reproduction utilise le runtime Babet réel ;
- une application tronquée de 10 ou 60 octets exécutait le script disque passé
  en argument. Le lot 14 corrigeait les erreurs d'accès, mais pas cette ambiguïté
  préexistante entre absence de ZIP et application endommagée ;
- après une copie EXDEV, un remplacement déterministe du chemin source juste
  après publication de la destination entraînait la suppression du remplaçant
  jamais copié. Ce défaut était déjà présent avant le lot 14.

Le correctif retient une identité explicite dans l'image chargée. Le builder
copie le runtime et le ZIP dans sa sortie temporaire privée, exige un unique
descripteur valide, puis inscrit le mode application et les bornes exactes du
ZIP avant publication atomique. Au démarrage, le runtime nu ignore les signatures
ZIP accidentelles ; l'application marquée doit avoir une archive de la bonne
taille, une fin valide et un `main.lua` lisible. Toute erreur constatée arrête
le lancement avant l'interprétation des arguments CLI. Les contrôles d'accès
et de lecture du lot 14 sont conservés.

Cela remplace l'ancien critère d'identité fondé sur la présence de `main.lua` :
les deux critères ne coexistent pas comme sources de vérité. Le marqueur est
effectivement référencé et lu en volatile ; un harnais GCC `-O3 -flto` avec
`--gc-sections` confirme sa conservation et la lecture des valeurs patchées.
L'attribut `used` seul ne garantit pas cette conservation à l'édition de liens.
Le checksum du descripteur n'est pas une authentification cryptographique et
ces vérifications ne prétendent pas détecter toute altération arbitraire d'ELF.

**Compatibilité :** reconstruire les applications avec le nouveau runtime pour
bénéficier du format et de la protection. Les anciennes applications gardent
leur ancien runtime. Une concaténation manuelle runtime + ZIP n'est plus une
application reconnue. Copier, renommer ou stripper le runtime nu avant packaging
reste possible ; ne pas stripper ni ajouter de données à l'application générée.
L'identité peut être lue en mémoire, mais l'accès à l'archive exige toujours
`/proc/self/exe` : ce lot n'ajoute pas de support sans procfs.

Pour EXDEV, le descripteur `O_PATH` de l'inode effectivement copié reste ouvert
jusqu'au contrôle du chemin source. `dev`, `ino` et type doivent correspondre
avant suppression. Un remplacement détecté est conservé ; la destination déjà
publiée reste disponible et l'opération renvoie une erreur. Garder le descripteur
ouvert empêche la réutilisation de cet inode avant la comparaison. **Limite :**
`lstat` suivi d'`unlink` n'est pas une suppression conditionnelle atomique ;
il faut éviter les mutations concurrentes de l'arbre pendant son déplacement.

## Contrats conservés et limites précises

### Chargement embarqué et bibliothèques natives

Le runtime reste conçu pour des scripts de confiance. Le mode généré inclut
le runtime et les modules empaquetés ; il n'impose pas une origine exclusivement
embarquée à tous les chargements.

Pour un module non déjà chargé, l'ordre est `package.preload`, chargeur du ZIP,
puis chargeurs Lua ordinaires. Si aucun candidat embarqué n'existe, ces derniers
peuvent chercher sur disque via `package.path` ou `package.cpath`. Une erreur
sur une entrée embarquée présente interrompt le chargement. Les workers
embarqués suivent la même politique. `package.loadlib` reste accessible.

Les modules natifs Lua doivent correspondre à l'ABI Lua ; ils ne sont pas
interchangeables avec l'API des plugins Babet. Le chargeur de plugins Babet
reste refusé dans une application générée. Le code natif chargé est du code
de confiance exécuté dans le processus, sans sandbox.

Références : `src/project_core/embedded_searcher.cpp`, initialisation de
`src/main.cpp` et `src/lua_bindings/workers.cpp`, guides
`docs/fr/getting-started.md` et `docs/en/getting-started.md`.

Retirer les chargeurs disque ou `package.loadlib` serait une évolution de
compatibilité à définir séparément. Le lot 13 corrige la description du
comportement existant.

### Permissions de `writeFileAtomic`

Le mode final par défaut reste **0644 exact**, y compris lors d'un remplacement
avec `overwrite = true`. Le mode de l'ancien fichier n'est pas conservé et
l'umask ne réduit pas ce mode final appliqué par `fchmod`. Un fichier privé
anciennement en 0600 peut donc devenir lisible par les autres utilisateurs
si l'appelant remplace son contenu sans préciser les permissions.

Pour écrire ou remplacer un fichier qui doit rester privé :

```lua
local ok, err = babet.writeFileAtomic("token.bin", token, {
    overwrite = true,
    permissions = tonumber("600", 8),
})
assert(ok, err)
```

Sans `overwrite = true`, un fichier existant est refusé et conservé.
Ce contrat était déjà explicite dans `docs/fr/modules/write-file-atomic.md`
et `docs/en/modules/write-file-atomic.md` ; il a été recontrôlé dans
`src/project_core/atomic_file.hpp` et `atomic_file.cpp`. Une politique de
préservation automatique des droits demanderait une décision distincte.

### État global, sortie et commandes des workers

- Configurer l'environnement, le répertoire courant et la locale **avant**
  `workers.spawn`, `gui.available()` ou `gui.init()`. La restriction reste
  permanente après le point de gel, même si le chargement GTK échoue ou si
  les workers sont ensuite terminés. Les consultations restent disponibles.
- Cette protection couvre les API Lua de Babet. Les hôtes d'embedding et
  plugins restent responsables de leurs propres threads et mutations directes
  de la libc. Il ne s'agit pas d'une interception universelle de `setenv`,
  `chdir` ou `setlocale` dans tout code natif.
- La sortie CLI par `os.exit` ne lance plus les callbacks natifs `atexit` ni
  les destructeurs statiques après son nettoyage explicite. Le retour normal
  conserve son autre chemin de terminaison. Avec fermeture Lua demandée,
  les finaliseurs peuvent attendre des workers : ce n'est pas une garantie
  de sortie à durée bornée. Voir `docs/fr/runtime-exit.md`.
- Les versions worker de `os.execute` et `io.popen` restent bloquantes.
  L'annulation coopérative du worker ne tue pas automatiquement la commande.
  Les fonctions standard de l'état principal ne sont pas remplacées par le
  lot 10.

### Autorités TLS

Un `ca_cert` non vide remplace les CA par défaut pour HTTP et `download`.
Pour socket TLS, STARTTLS et WSS, il complète les autorités déjà chargées.
La vérification de l'identité reste nécessaire et ces options ne constituent
pas du pinning d'un certificat ou d'une clé. Le lot 11 préserve cette
différence et la couvre avec des essais utilisant deux autorités distinctes.

## Affirmations du premier audit à ne pas reprendre telles quelles

- La locale française ne rendait pas systématiquement invalide
  `tonumber("1.5")` dans la version Lua examinée. La mutation concurrente
  de la locale constituait néanmoins un risque à traiter.
- `proc:kill("TERM")` n'était pas l'API de cette version : `kill()` n'accepte
  pas d'argument ; `terminate(grace?)` commence par SIGTERM. Le défaut du
  masque enfant a été reproduit en envoyant le signal de l'extérieur.
- Le comportement du shell vis-à-vis d'un masque hérité dépend aussi de la
  forme de la commande. Un cas avec `exec` explicite conserve ce masque
  avec les shells testés. La correction du lot 10 le vide avant le shell.
- Aucun crash GLib/getenv ni crash OpenSSL à la sortie n'a été reproduit dans
  cette campagne. Pour GTK, le test du lot 12 utilise une bibliothèque de
  test qui démarre un vrai pthread et démontre que l'ancienne garde laissait
  encore passer les mutations. Les protections ne doivent pas être présentées
  comme la preuve rétrospective d'un crash dans une version réelle de GLib.
- Le repli disque ne prouve pas un contournement de sandbox ; Babet n'en
  promet pas. Le mode 0644 et la différence des CA étaient des comportements
  existants à expliciter, pas des erreurs de transcription.
